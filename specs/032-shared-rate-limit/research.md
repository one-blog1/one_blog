# Research: 요청 제한 기록 공유

## R1. 어디에 기록하나

- **Decision**: 운영 DB(MySQL)에 테이블 `rate_limit_hits`를 두고 두 앱이 같이 쓴다.
- **Rationale**: 앱 2개가 이미 같은 DB를 쓴다. 새 저장소(Redis)를 두지 않는다(4.3, constitution V). ShedLock(`shedlock`)도 같은 방식으로 앱끼리 나눈다.
- **Alternatives**: Redis → 서버·운영이 하나 더 늘어남(4.3에서 서버를 늘릴 때 정하기로 함). 바깥 nginx `limit_req` → 회원 기준 제한(신고·좋아요)은 못 하고, 로그인만 따로 두면 규칙이 두 곳에 흩어짐.

## R2. 세는 방식

- **Decision**: 지금과 같은 슬라이딩 윈도. 요청마다 기록 한 줄, "최근 N분 기록 수 ≥ max면 거절, 아니면 한 줄 더함".
- **Rationale**: 지금 동작과 같아 테스트·문서를 바꾸지 않는다. 고정 창(분 단위 카운터 한 줄)은 줄이 적지만 창 경계에서 최대 2배가 통과해, 이번에 없애려는 문제와 같은 꼴이 된다.
- **동시 요청**: 세기와 쓰기 사이에 잠금을 걸지 않는다. 같은 순간에 두 앱이 받으면 한두 번 더 통과할 수 있다(스펙 Edge Case). `SELECT ... FOR UPDATE`는 로그인마다 행 잠금 대기를 만들어 빼다.

## R3. 시각 기준

- **Decision**: DB 시각(`NOW(6)`, 기록의 `created_at` 기본값)으로 센다. 앱 시각을 넘기지 않는다.
- **Rationale**: 두 앱의 시계가 조금 달라도 기준이 하나다. DB 세션 시간대는 이미 +09:00(application.yml `connection-init-sql`).

## R4. 트랜잭션

- **Decision**: 기록·세기는 부르는 쪽 트랜잭션과 **따로**(새 트랜잭션, `REQUIRES_NEW`) 커밋한다.
- **Rationale**: 제한을 거는 서비스(비밀번호 재설정·신고 등)는 뒤에서 예외가 나면 트랜잭션을 되돌린다. 같은 트랜잭션이면 실패한 시도의 기록도 되돌아가서, 실패를 반복하는 매크로가 세어지지 않는다. 지금(메모리)은 예외와 상관없이 세어진다 — 그 동작을 지킨다.
- **연결 수**: 바깥 트랜잭션이 연결 하나를 쥔 채 하나를 더 쓴다. 기본 풀(10개)에서 짧게 쓰고 돌려줘 문제없다.

## R5. 키를 그대로 둘까

- **Decision**: `action`(제한 이름, 예: `login`)은 그대로, 대상(IP 또는 회원 번호)은 **HMAC-SHA256 해시**(`key_hash`, 64자)로 둔다. 비밀 값은 블랙리스트와 같은 `app.privacy.hash-pepper`(PRIVACY_HASH_PEPPER, 없으면 CODE_PEPPER).
- **Rationale**: IP는 개인정보라 원문을 DB에 남기지 않는다(REQ-002 민감 정보 저장 규칙, 4.6). 단순 SHA-256은 IPv4 전체를 금방 대조할 수 있어 비밀 값을 섞는다. 같은 값은 늘 같은 해시라 세는 데 문제없다.
- **Alternatives**: 원문 저장 → 1시간 안에 지우더라도 원칙에 어긋남.

## R6. 정리

- **Decision**: 두 곳에서 지운다.
  1. 기록할 때 그 대상의 오래된 기록(창 밖)을 같이 지운다 → 한 대상의 줄 수가 max 근처로 유지.
  2. 04:00 배치(`CleanupTask`)가 1시간(가장 긴 창, 신고)보다 오래된 기록을 모두 지운다 → 다시 오지 않는 IP의 기록 정리.
- **Rationale**: 1만으로는 다시 오지 않는 대상의 기록이 남고, 2만으로는 좋아요처럼 잦은 요청이 하루 동안 쌓인다.

## R7. DB가 안 될 때

- **Decision**: 기록·세기에서 DB 오류가 나면 경고 로그를 남기고 **통과**시킨다.
- **Rationale**: 요청 제한은 보조 장치다. DB가 흔들릴 때 로그인 전체를 막으면 더 큰 장애가 된다. 계정별 잠금(5번, `users.failed_login_count`)은 그대로 지킨다.

## R8. 테스트

- **Decision**:
  - `RateLimiterIntegrationTest`(DB): 같은 DB를 쓰는 `RateLimiter` 두 개(앱 2개 흉내)에 번갈아 요청해 합쳐서 막히는지, 창이 지나면 다시 되는지(기록 시각을 SQL로 과거로 옮겨 확인), 해시가 원문이 아닌지, 정리가 되는지.
  - 기존 `RateLimiterTest`(단위, 메모리 판단 `tryAcquire`)는 메모리 방식이 없어지므로 "꺼져 있으면 검사하지 않음"만 남기고 나머지는 통합 테스트로 옮긴다.
  - 테스트 설정의 `app.rate-limit.enabled=false`는 그대로(다른 테스트가 같은 IP로 수백 번 로그인).
