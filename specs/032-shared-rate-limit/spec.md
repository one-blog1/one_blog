# Feature Specification: 요청 제한 기록 공유

**Feature Branch**: `feature/shared-rate-limit`

**Created**: 2026-10-16

**Status**: Draft (specify 확인 대기)

**Input**: 보안 미구현 항목 중 "같은 IP 로그인 제한(SEC-03)"의 남은 일. 029 테스트 보강 때 발견: 요청 제한 기록이 앱 메모리에 있어 운영 앱 2개(D-135 무중단 배포)가 따로 센다.

**관련 요구사항**: SEC-03(같은 IP 로그인 10분 30번, D-80), USR-08(이메일 찾기·비밀번호 재설정 같은 IP 10분 5번), 6.6 트래픽 제한, SCL-01(서버 메모리에 상태를 두지 않음), D-105, D-135, constitution IV

## 지금 상태

- 요청 제한(`RateLimiter`)은 "최근 N분 동안 몇 번"을 **앱 메모리**에 기억한다(슬라이딩 윈도).
- 운영은 앱 2개가 같이 떠 있고 바깥 프록시가 요청을 나눠 보낸다(D-135). 그래서 같은 IP라도 요청이 두 앱에 나뉘면 각 앱이 따로 세어, **제한이 최대 2배로 느슨**하다(예: 로그인 10분 30번 → 실제 최대 60번).
- 배포로 앱이 바뀌면 그 앱의 기록이 사라져 제한이 처음부터 다시 센다.
- 접속 IP 읽기는 이미 해결됨(0.19, `FORWARD_HEADERS_STRATEGY=native`).

지금 거는 제한:

| 이름 | 기준 | 횟수 | 근거 |
|---|---|---|---|
| 로그인(회원·관리자) | IP | 10분 30번 | SEC-03, D-80, D-105 |
| 가입 인증번호 | IP | 10분 10번 | USR-02, 6.6 |
| 비밀번호 재설정 | IP | 10분 5번 | USR-06, USR-08 |
| 이메일 찾기 | IP | 10분 5번 | USR-08 |
| 비밀번호 다시 확인 | 회원 | 10분 5번 | 계정 관리 |
| 신고 | 회원 | 1시간 20번 | 6.6 |
| 좋아요·팔로우·구독 누르기 | 회원 | 1분 60번 | 6.6 |

## 바뀌지 않는 것

- 제한 기준·횟수·시간, 넘었을 때의 응답(429, `TOO_MANY_REQUESTS`, 다시 시도까지 남은 초)은 그대로다.
- 화면·API 모양은 바뀌지 않는다.
- 테스트 설정의 "요청 제한 끄기"(`app.rate-limit.enabled=false`)는 그대로 둔다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 제한이 앱 수와 상관없이 정확하다 (Priority: P1)

같은 IP에서 로그인을 계속 시도하는 매크로는 앱이 몇 개 떠 있든 10분에 30번에서 막힌다.

**Why this priority**: SEC-03의 목적(여러 계정을 돌려 가며 시도하는 매크로 막기, D-80)이 지금은 절반만 지켜진다.

**Independent Test**: 앱 두 개(같은 DB)에 같은 IP로 로그인 요청을 번갈아 보내면, 합쳐서 31번째가 429다.

**Acceptance Scenarios**:

1. **Given** 같은 DB를 쓰는 앱 A·B, **When** 같은 IP로 A에 15번, B에 15번 로그인 요청, **Then** 31번째 요청은 어느 앱으로 가든 429다.
2. **Given** 10분이 지난 뒤, **When** 다시 요청, **Then** 다시 받는다(슬라이딩 윈도, 지금과 같은 규칙).
3. **Given** 앱이 새 버전으로 바뀌어도(배포), **When** 같은 IP가 이어서 요청, **Then** 배포 전 기록까지 합쳐 센다.

---

### User Story 2 - 모든 요청 제한에 같은 방식 (Priority: P2)

위 표의 제한 7가지가 모두 앱끼리 공유된다.

**Why this priority**: 이메일 찾기·비밀번호 재설정(10분 5번)은 2배가 되면 의미가 크게 줄어든다. 방식을 하나로 두면 단순하다(V).

**Independent Test**: 각 제한을 횟수만큼 채운 뒤 다음 요청이 429다(기존 테스트 + 공유 확인).

---

### User Story 3 - 기록이 쌓이지 않는다 (Priority: P3)

지난 기록은 정리되어 저장 공간이 계속 늘지 않는다.

**Acceptance Scenarios**:

1. **Given** 제한 시간(가장 긴 것 1시간)이 지난 기록, **When** 정리가 돌면, **Then** 지워진다.

### Edge Cases

- **동시에 들어온 요청**: 두 앱이 같은 순간에 같은 IP를 받으면 한두 번 더 통과할 수 있다. 지금처럼 앱마다 따로 세는 것(최대 2배)보다 훨씬 좁고, 매크로 막기에는 충분하다. 정확히 막기 위해 잠금을 걸지는 않는다(로그인 속도에 영향).
- **DB가 느리거나 잠시 안 될 때**: 요청 제한 때문에 로그인 자체가 실패하지 않게, 기록을 못 읽으면 그 요청은 통과시키고 로그를 남긴다(사용자 기능 우선). 로그인 잠금(계정별 5번)은 따로 있어 그대로 지킨다.
- **매크로가 많은 IP로 몰아칠 때**: 기록 줄 수가 늘지만, 제한 시간이 지나면 정리된다. 지금처럼 앱 메모리를 지키려고 기록을 통째로 버리지 않는다.
- **좋아요 같은 잦은 요청**: 누를 때마다 기록이 하나 쌓인다. 좋아요 자체도 DB에 쓰는 일이라 부담은 비슷하다.

## Requirements *(mandatory)*

- **FR-001**: 요청 제한 기록을 앱 메모리가 아니라 모든 앱이 같이 보는 DB에 둔다(SCL-01).
- **FR-002**: 판단 규칙은 지금과 같다: 최근 N분 안의 기록이 max개 이상이면 거절(429), 아니면 기록을 남기고 통과.
- **FR-003**: 위 표의 제한 7가지가 모두 이 방식을 쓴다. 횟수·시간·기준은 바꾸지 않는다.
- **FR-004**: 기록을 읽거나 쓰지 못하면 요청을 통과시키고 경고 로그를 남긴다.
- **FR-005**: 제한 시간이 지난 기록은 정리한다(가장 긴 제한 1시간보다 오래된 것).
- **FR-006**: DB 구조는 Crowfoot ERD를 먼저 고치고 Flyway 마이그레이션(V24)으로 더한다(constitution IV).
- **FR-007**: 문서: `security-status.md`(SEC-03 해결), `DEPLOY.md`의 "로컬과 같은 DB를 쓰는 동안" 안내(개발 DB 분리 완료, 2026-10-16), `RateLimiter` 주석.

### Key Entities

- **요청 기록**: 어떤 제한(이름), 누구(IP 또는 회원 번호), 언제. 제한 시간이 지나면 지운다. 개인정보를 줄이기 위해 IP는 원문 대신 해시로 둘지 plan에서 정한다.

## Success Criteria *(mandatory)*

- **SC-001**: 앱 2개(같은 DB) 환경에서 같은 IP 로그인 31번째가 429다(테스트로 확인).
- **SC-002**: 기존 요청 제한 테스트가 그대로 통과한다.
- **SC-003**: 1시간보다 오래된 기록은 정리 뒤 남지 않는다.
- **SC-004**: 로그인 응답 시간이 눈에 띄게 늘지 않는다(기록 한 줄 쓰기·세기 한 번).

## Assumptions

- 운영 DB 하나를 두 앱이 같이 쓴다(지금 구조).
- Redis 같은 저장소는 두지 않는다(4.3: 서버를 늘릴 때 정함, constitution V).
- 정리는 04:00 배치에 더하거나, 기록할 때 같이 지운다(plan에서 정함).

## 이번에 하지 않음

- 제한 횟수·기준 바꾸기, 관리자 화면에 제한 상태 보여 주기
- 앱 포트 바깥 접속 막기(운영 서버 확인 뒤 따로), 운영 응답 헤더 확인
