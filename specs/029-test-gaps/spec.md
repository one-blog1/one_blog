# Feature Specification: 테스트 보강 (테스트 공백 1~3번)

**Feature Branch**: `feature/test-gaps` | **Created**: 2026-10-15 | **Status**: Draft (specify 확인 대기)

**Input**: "그냥 너가 테스트 케이스보고 추가하거나 수정해야할 내용 분석해봐", "3장에 국한되는게 아니라 모든 요구사항 그리고 요구사항만 보지말고 현재 구현되는 기능에 필요한 테스트가 없으면 그것도 찾아봐", 분석 결과 중 "중간까지"(1. 기존 테스트 고치기, 2. 높음, 3. 중간)

**관련 요구사항**: 2장 권한표, USR-05~09, BLG-01·08·09·11~13, SOC-03·05·06, BRD-02·05·07~10·12, ADM-02~04·06·07, SEC-02~05·07~10·13, SCL-03, 4.4(가림), 4.5(보관·삭제), 6.1·6.3·6.5·6.7, D-36, D-43, D-60, D-71, D-86, D-95, D-96, D-102, D-106, D-107, D-114, D-126, D-128, D-138

## 무엇을 하는가

지금 테스트는 통합 216개·단위 55개다. 요구사항 1~8장·결정 기록과 지금 코드를 테스트와 대조한 결과, 다음 세 가지를 이번에 처리한다.

1. **기존 테스트 고치기**: 규칙이 깨져도 통과할 수 있는 기존 테스트 7곳
2. **높음**: 보안·권한·개인정보·되돌릴 수 없는 삭제를 확인하는 테스트 추가
3. **중간**: 기능은 있는데 테스트가 없는 것 추가

## 바뀌지 않는 것

- **기능 코드는 바꾸지 않는다.** 바꾸는 것은 테스트와 테스트 도우미뿐이다. 테스트가 버그를 찾으면 고치기 전에 사용자에게 묻는다.
  - 예외: 04:00 배치 잠금은 이번에 고친다 (US6-12, 사용자 결정 2026-10-15).
- 요구사항 문서는 바꾸지 않는다.
- 테스트 DB와 CI 설정은 그대로 둔다. 테스트용 설정 파일의 기본값(요청 제한 끔, 사람 확인 키 없음, Secure 쿠키 끔)도 그대로 둔다. 이 기능들을 켜고 확인하는 테스트만 따로 켠다.
- 분석의 4번(낮음), 5번(화면 스크립트·배포 스크립트), 6번(요구사항에 있는데 코드에 없는 것)은 이번 범위가 아니다.

## 사용자 시나리오

"사용자"는 이 서비스를 개발·운영하는 사람이다. 기대하는 가치는 "규칙을 깨는 변경을 하면 CI가 실패해서 배포 전에 알 수 있다"이다.

### US1 - 기존 테스트가 실제 규칙을 확인한다 (P1)

**Why**: 잘못된 이유로 통과하는 테스트는 규칙이 깨져도 초록불이라, 테스트가 없는 것보다 위험하다.

**Independent Test**: 아래 규칙을 하나씩 일부러 깨면, 고친 테스트가 실패한다.

1. **Given** 테스트 회원마다 다른 전화번호(와 이름)를 쓸 수 있을 때, **When** 한 회원을 강퇴하면, **Then** 그 회원만 블랙리스트에 걸리고 다른 회원은 참여할 수 있다.
   - 블랙리스트 테스트는 이메일만 같은 경우와 전화번호만 같은 경우를 따로 확인한다.
   - 기존 테스트는 지금처럼 같은 기본값을 써도 된다.
2. **Given** 가입 입력 검사, **When** 비밀번호·닉네임·전화번호를 하나씩만 틀리게 보내면, **Then** 그 칸의 오류만 온다.
3. **Given** 정하지 않은 주소, **When** 실제로 있는 파일이지만 허용 목록에 없는 주소를 요청하면, **Then** 거부된다. "없는 파일이라 404"와 구분한다.
4. **Given** 멤버 관리 권한이 있는 부블로그장이 신고 대상일 때, **When** 신고 목록을 보면, **Then** 자기에 대한 신고는 보이지 않는다 (D-95). 권한이 없어서 거부되는 경우와 구분한다.
5. **Given** 블로그 이름·소개에는 없고 블로그 태그에만 있는 단어, **When** 블로그 검색을 하면, **Then** 그 블로그가 나온다 (BLG-03).
6. **Given** 팔로우가 실제로 된 상태(1건)에서, **When** 차단하면, **Then** 팔로우가 0건이 된다 (SOC-05).
7. **Given** 이번에 손대는 테스트에서 서버가 거부할 때, **Then** 상태 코드와 함께 오류 코드도 확인한다. 같은 403·409가 다른 이유로 나와도 통과하지 않게 한다.

### US2 - 권한 경계를 넘는 요청은 거부된다 (P1)

**Why**: SEC-07·SEC-11, 헌법 III. 지금 거부 테스트는 대부분 "블로그가 없는 회원"으로만 해서, 다른 블로그의 관리자나 부블로그장이 경계를 넘는 경우가 비어 있다.

1. **다른 블로그의 블로그장**: B 블로그의 블로그장이 A 블로그에 다음을 하면 거부된다.
   - 글 삭제, 카테고리 관리, 멤버 제재, 정보 수정, 폐쇄
   - A 블로그 주소에 B 블로그의 신고·문의 번호나 B 멤버 번호를 넣은 요청 (없는 것으로 처리)
2. **부블로그장**: 권한 세 개를 모두 받았어도 블로그장 전용 기능은 거부된다 (2장, D-71, D-138).
   - 부블로그장 지정·권한 변경 (자기 권한 올리기 포함)
   - 위임 요청
   - 폐쇄와 폐쇄 철회
   - 공유 링크 다시 만들기
3. **제재 위계** (3.7, D-43): 부블로그장끼리 서로 제재할 수 없고 자기 자신도 제재할 수 없다. 블로그장은 부블로그장을 제재할 수 있다.
4. **신고 처리 경계** (D-95, D-96):
   - 신고 대상 본인인 부블로그장은 그 신고를 처리할 수 없다.
   - 관리자에게 가는 신고는 블로그 쪽에서 처리할 수 없고, 블로그 신고는 관리자 쪽에서 처리할 수 없다.
5. **비공개 블로그 좋아요**: 멤버가 아니면 거부된다 (2장).
6. **소셜 계정**: 이미 다른 회원에 연결된 소셜 계정은 내 계정에 연결할 수 없다 (USR-09, D-126).
7. **공유 링크** (BLG-01): 블로그장이 다시 만들면 새 링크로는 들어가고, 이전 링크로는 들어갈 수 없다. 일부 공개가 아닌 블로그는 공유 링크를 만들 수 없다.

### US3 - 로그인·계정 보안 규칙이 실제로 동작한다 (P1)

**Why**: 사람 확인, 요청 제한, Secure 쿠키, CSRF의 실제 경로는 테스트 설정에서 꺼져 있거나 테스트 도구가 건너뛰어서, 지금은 이 코드가 한 번도 실행되지 않는다.

1. **사람 확인** (SEC-13, 6.7):
   - 3번 틀린 뒤에는 사람 확인 없이 로그인할 수 없다. 확인을 통과하면 로그인된다.
   - 관리자 로그인은 사람 확인을 하지 않는다.
2. **요청 제한** (SEC-03, D-80, USR-08):
   - 같은 IP 로그인 요청은 10분에 30번까지다. 31번째는 거부되고, 관리자 로그인도 같은 제한에 들어간다.
   - 이메일 찾기는 같은 IP 10분에 5번까지다.
3. **비밀번호 재설정** (SEC-05, USR-06, USR-08):
   - 번호는 30분이 지나면 쓸 수 없다.
   - 5번 틀리면 맞는 번호도 쓸 수 없다.
   - 이메일 찾기 임시 토큰은 10분이 지나면 쓸 수 없다.
   - 잠긴 계정도 재설정하면 바로 로그인할 수 있다.
4. **비밀번호 규칙** (SEC-02, 6.7): 8자·15자는 통과하고, 7자·16자, 영문·숫자·특수문자 중 하나라도 빠진 경우, 공백이 든 경우는 거부된다. 가입·변경·재설정 세 곳 모두 같다.
5. **CSRF** (SEC-10): 화면이 받은 CSRF 쿠키 값을 헤더로 보내면 성공하고, 틀린 값이나 헤더 없음은 거부된다. 테스트 도구의 우회를 쓰지 않고 실제 경로로 확인한다.
6. **쿠키** (SEC-04): 운영 설정(Secure 켬)에서 로그인·재확인·가입 쿠키가 Secure·HttpOnly다. "로그인 유지"를 체크하지 않으면 두 로그인 쿠키 모두 브라우저를 닫으면 사라지고, 체크하면 14일이다.
7. **재확인** (D-102): 비밀번호 재확인은 10분이 지나면 다시 해야 한다.

### US4 - 개인정보가 새지 않고 규칙대로 지워진다 (P1)

**Why**: 4.4·4.5·4.6, 헌법 III. 지금 테스트는 가림·탈퇴 정리·검색 제외의 일부만 확인한다.

1. **블랙리스트** (BLG-11): 강퇴 → 탈퇴 → 같은 이메일로 다시 가입하면 그 블로그에 참여할 수 없다. 다른 이메일·같은 전화번호도 마찬가지다. 둘 다 다르면 참여할 수 있다.
2. **가림** (4.4):
   - 블로그장과 멤버 관리 부블로그장이 보는 멤버 목록의 이메일·전화번호가 정해진 형식으로 가려진다.
   - 관리자의 회원 상세도 가려진다. 전체 보기는 기록이 남는 별도 요청으로만 된다.
   - 다른 회원의 프로필 응답에는 이메일·이름·전화번호가 없다.
   - 이름 가림(2글자·3글자·긴 이름)이 정해진 형식이다.
3. **탈퇴** (USR-05, 4.5):
   - 탈퇴 즉시 구독·대기 중인 참여 신청·최근 검색어를 정리하고, 프로필에서 찾을 수 없다.
   - 29일째에는 개인정보가 남아 있다.
   - 31일째에는 이름·닉네임·전화번호·소개·프로필 사진(저장된 파일 포함)이 지워진다.
4. **검색 제외** (6.1, BLG-01): 다음은 글 검색과 블로그 검색에 나오지 않는다.
   - 일부 공개 블로그, 숨긴 블로그, 폐쇄된 블로그
   - 내가 차단한 회원의 글
5. **피드** (BRD-09, D-37, D-50, D-113):
   - 구독한 블로그가 비공개로 바뀌면 멤버가 아닌 구독자의 구독 탭에서 빠진다.
   - 일부 공개 블로그를 링크로 구독하면 구독 탭에 나온다.
   - 내가 정지된 블로그의 글은 "내 블로그" 새 글에서 빠진다.
6. **영상 썸네일** (D-128, SSRF 방어):
   - 허용하지 않은 주소로 가는 리다이렉트는 따라가지 않는다. 리다이렉트는 3번까지만 따라간다.
   - 2MB를 넘는 사진은 버리고, 글은 썸네일 없이 저장된다.

### US5 - 삭제 배치는 정한 것만, 정한 때에 지운다 (P1)

**Why**: 4.5, D-60, D-86. 삭제는 되돌릴 수 없다. 너무 일찍 지우거나 엉뚱한 것을 지우면 복구할 수 없다.

1. **폐쇄된 블로그** (BLG-09, D-86):
   - 29일째에는 내용이 그대로다.
   - 31일째에는 글·댓글·카테고리·블로그 태그·구독·사진(저장된 파일 포함)·블랙리스트·해제 문의가 지워진다.
   - 30일 안에는 다른 회원이 같은 주소로 블로그를 만들 수 없고, 그 뒤에는 만들 수 있다.
2. **30일 지난 삭제 대상** (4.5):
   - 따로 지운 댓글은 31일째 지워진다. 살아 있는 답글이 달린 댓글은 남는다.
   - 지운 표시가 된 사진, 글에 붙지 않은 업로드, 쓰지 않는 배너 사진은 31일째 행과 저장된 파일이 지워진다.
   - 29일째에는 모두 남아 있다.
3. **1년 보관 기록** (4.5, D-60): 신고·제재·관리자 활동 기록은 1년이 지난 것만 지워지고, 1년이 안 된 것은 남는다.
4. **그 밖의 정리** (6.7, 4.5): 보관 기간(30일·7일)이 지난 알림은 실제로 지워진다. 쓰거나 만료된 인증번호·임시 토큰도 지워진다.
5. **블로그장 경고** (ADM-07, D-30): 1년 안의 경고만 센다. 1년 넘은 경고 2건에 새 경고 1건이면 권한이 박탈되지 않는다.

### US6 - 테스트가 없던 기능을 확인한다 (P2)

**Why**: 아래 기능은 동작하지만 이를 부르거나 결과를 확인하는 테스트가 없어, 고장 나도 모른다.

1. **테스트가 부르지 않던 API·화면**:
   - 관리자: 블로그 목록·검색(블로그장·멤버 수·글 수), 글 목록, 회원 상세, 댓글 삭제 (작성자에게 사유와 함께 알림, ADM-03, D-107)
   - 위임: 요청 확인, 요청 취소, 거절 (블로그장에게 결과 알림)
   - 프로필 사진: 올리고 바꾸기 (내 사진 → 프로필 반영)
   - 알림: 자세히 보기 (D-107: 글이 지워졌으면 바로가기 없음, 댓글만 지워졌으면 그 글로), 모두 읽음, 알림 설정 조회
   - 그 밖: 블랙리스트 문의 거절 (문의한 사람에게 알림), 탈퇴 화면 정보 (블로그장인 블로그 목록), 소셜 가입 그만두기 (가입 대기 정보가 지워짐)
   - 화면 주소: 글쓰기, 글 수정, 블로그 관리
2. **관리자 활동 기록** (SEC-09, ADM-06): 다음 조치마다 기록이 1건 남는다.
   - 블로그·글·댓글 숨김과 숨김 해제
   - 글·댓글 삭제
   - 공지 작성·삭제
   - 신고 처리
   - 블로그장 경고, 강제 폐쇄
3. **알림** (3.6): 누가 내 블로그를 구독하면 블로그장에게 알림이 간다. 관리자가 내 댓글을 지우면 나에게 알림이 간다.
4. **위임** (BLG-08):
   - 7일 동안 답이 없으면 자동 취소되고 블로그장에게 알림이 간다.
   - 받는 사람이 블로그 개수 제한에 걸리면 수락할 수 없다.
   - 블로그장 권한이 박탈되면 대기 중인 위임 요청이 취소된다.
5. **폐쇄** (BLG-09, USR-05):
   - 1일 전 알림이 간다.
   - 폐쇄 예정 중인 블로그의 블로그장은 탈퇴할 수 없다. 폐쇄가 끝나면 탈퇴할 수 있다.
6. **정지** (BLG-13, 3.7):
   - 기간이 끝나면 다시 들어갈 수 있다.
   - 영구 정지는 풀리지 않는다.
   - 정지 중에도 다른 블로그는 쓸 수 있다.
7. **강퇴 승계** (ADM-01, ADM-07): 부블로그장이 여럿이면 가장 먼저 부블로그장이 된 사람이 블로그장이 된다.
8. **부블로그장 권한별** (D-71, D-138):
   - 글 관리 권한: 카테고리 관리, 블로그 공지 쓰기
   - 멤버 관리 권한: 신고 보기·처리
   - 각 권한이 없으면 거부되고, 있으면 된다.
9. **관리자 열람** (ADM-02, D-106): 일부 공개 블로그와 숨긴 글을 열면 기록이 남는다. 지운 글은 열 수 없다.
10. **신고** (SOC-06, ADM-04, 6.5):
    - 같은 대상은 2주가 지나면 다시 신고할 수 있다.
    - 프로필 신고는 관리자에게 간다.
    - 관리자가 신고를 처리하면서 글을 지울 수 있다.
    - 신고 당시 내용이 남아 있어, 글이 지워져도 무엇을 신고했는지 보인다.
    - 같은 대상에 대한 여러 신고를 한 번에 처리하면 신고자마다 결과 알림이 간다.
11. **업로드 위치 정보** (6.3): GPS가 든 사진을 올리면 저장된 파일에는 GPS가 없다.
12. **04:00 배치 잠금** (SCL-03):
    - 한 서버가 잠금을 가진 동안 다른 서버는 배치를 건너뛴다.
    - 잠금 시간이 지나면 다시 잡을 수 있다.
    - 매일 04:00(Asia/Seoul)에 돌도록 정해져 있다.
    - **고친다 (2026-10-15 결정)**: 지금은 배치가 끝나자마자 잠금이 풀려서, 늦게 도착한 다른 서버가 같은 날 배치를 한 번 더 돌 수 있다. 배치가 끝나도 잠금을 최소 5분 유지해, 한 서버가 끝낸 뒤 다른 서버가 와도 건너뛰게 한다 (SCL-03 "한 번만 실행"에 맞춤).
    - 한 서버가 배치를 끝낸 직후 다른 서버가 오면 건너뛴다. 이 테스트는 고치기 전 코드에서는 실패해야 한다.

### Edge Cases

- 테스트가 요구사항과 다른 동작을 찾으면 그 테스트는 요구사항 기준으로 쓴다.
  - 바로 고치지 않고 사용자에게 알린다.
  - 사용자가 고치기로 하면 같은 브랜치에서 고치고 결정 기록을 남긴다. 따로 하기로 하면 그 테스트는 이유를 적어 비활성으로 두고 후속 작업에 남긴다.
- 요구사항과 코드가 다르다고 이미 알려진 것(분석 6번)은 지금 코드 동작을 기준으로 테스트하고, 테스트 설명에 그 사실을 적는다.
  - 예: "쓴 인증번호는 바로 삭제"(요구사항) ↔ "04:00 배치에서 삭제"(코드)
- 시간에 따라 달라지는 규칙(30분·10분·7일·30일·1년)은 실제로 기다리지 않는다. 저장된 시각을 과거로 바꾸거나 배치에 기준 시각을 넣어 확인한다.
- 자정·월말 같은 시각에 돌아도 결과가 같아야 한다 (같은 날 조회수 등).
- 요청 제한·사람 확인·Secure 쿠키를 켠 테스트가 다른 테스트에 영향을 주면 안 된다.

## 요구사항

- **FR-001**: US1의 7개 항목을 고친다. 고친 테스트는 각 규칙을 깨면 실패해야 한다.
- **FR-002**: 테스트 회원을 만들 때 전화번호(와 이름)를 정할 수 있게 한다. 기존 호출은 그대로 동작한다.
- **FR-003**: US2~US5의 시나리오마다 그것을 확인하는 테스트가 하나 이상 있다.
- **FR-004**: US6의 시나리오마다 그것을 확인하는 테스트가 하나 이상 있다.
- **FR-005**: 꺼 둔 기능(요청 제한, 사람 확인, Secure 쿠키, 스케줄 잠금)은 그 기능을 확인하는 테스트에서만 켠다. 나머지 테스트의 설정은 바꾸지 않는다.
- **FR-006**: 외부 사이트(Turnstile, 영상 사이트, 소셜 사이트)에는 실제로 접속하지 않는다. 가짜를 쓰거나 테스트 안에서 띄운 서버를 쓴다.
- **FR-007**: 기능 코드는 바꾸지 않는다. 버그를 찾으면 Edge Cases의 절차를 따른다.
- **FR-010**: 04:00 배치 잠금은 배치가 끝나도 최소 5분 유지한다. 잠금을 잡은 서버만 잠금을 풀 수 있고, 최대 유지 시간(지금 1시간)은 그대로다.
- **FR-008**: 새 테스트와 고친 테스트에는 지금처럼 근거(요구사항 ID·결정 번호)를 클래스나 메서드 설명에 적는다.
- **FR-009**: 분석 항목과 테스트를 잇는 대조표를 남긴다. 분석 1~3번의 항목마다 어느 테스트가 확인하는지 적는다.

## Success Criteria

- **SC-001**: CI에서 전체 테스트가 통과한다.
- **SC-002**: 분석 1~3번의 항목(약 70개)마다 대응 테스트가 대조표에 있다. 테스트를 만들지 못한 항목은 이유와 함께 표시한다.
- **SC-003**: US1의 7개 규칙을 하나씩 일부러 깨면 해당 테스트가 실패한다. 확인 결과는 대조표에 적는다.
- **SC-004**: 기능 코드는 바뀌지 않는다. 배치 잠금(FR-010)과 사용자가 승인한 수정만 예외다.
- **SC-005**: CI 전체 테스트 단계 시간(지금 약 5분)이 5분 넘게 늘지 않는다.

## Assumptions

- **테스트 실행은 CI로만 한다.** 이 작업 공간은 Maven 저장소에 접속할 수 없어 테스트를 직접 돌릴 수 없다. `feature/test-gaps`에 push하면 CI만 돌고 배포는 되지 않는다(D-136).
- 테스트 DB는 지금처럼 테스트마다 비운다. 새 테스트도 같은 방식을 따른다.
- 이 작업으로 테스트가 대략 70~100개 늘어난다(통합 위주).
- 다른 세션에서 `feature/ci-test-stages`(스펙 028, D-140: CI 단계 나누기·E2E·SonarQube)를 진행 중이다. 그래서 이 스펙은 029다. 겹치는 파일은 없다(028은 CI·빌드 설정과 E2E 테스트, 029는 통합·단위 테스트).
  - 028의 테스트 이름 규칙을 따른다. DB가 필요한 테스트는 `...IntegrationTest`, DB 없는 테스트는 `...Test`로 이름을 짓는다.
  - 028이 먼저 합쳐지면 기능 브랜치 push에서는 단위 테스트만 돈다. 그때는 이 브랜치의 통합 테스트를 CI 직접 실행(전체 단계)으로 확인한다.
  - 028이 커버리지 보고서를 넣으므로, 합친 뒤에는 이번 보강 전후의 커버리지 숫자도 비교할 수 있다.
