# Feature Specification: 배포 단계별 테스트 (CI 단계 나누기 + 정적 분석)

**Feature Branch**: `feature/ci-test-stages` | **Created**: 2026-10-15 | **Status**: Draft (Q1~Q3 답 반영 2026-10-15)

**결정 (2026-10-15)**: Q1 스테이징은 만들지 않음, Q2 블루-그린 유지 + 운영 스모크 + 자동 되돌리기(카나리 없음), Q3 품질 게이트를 통과하지 못하면 merge를 막고 개선부터 한다

**Input**: "매번 돌리지 말고 저 이미지대로 단계 설정해줘", "소나큐브 사용하는 법". 이미지(배포 단계마다 다른 테스트가 지킨다, Shift Left):
1 PR/커밋 — 단위 테스트·정적 분석(SonarQube)·커버리지 → 2 main 머지 — 전체 테스트·통합 테스트·배포 파일 빌드 → 3 스테이징 — E2E·성능/부하·QA → 4 운영 — 스모크·카나리·모니터링/자동 롤백

**관련 요구사항**: D-117(CI), D-118·D-120(배포), D-135(블루-그린), D-136·D-137(브랜치·스펙 단위), constitution "개발 흐름"·V(단순함), 새 결정 D-140

## 지금 상태 (바꾸기 전)

- CI는 모든 push·PR에서 같은 일을 한다: 전체 테스트 265개(통합 32개 클래스 + 단위 13개 클래스) → jar 실행 확인 → Docker 실행 확인. 매번 MySQL을 띄운다.
- 정적 분석·커버리지 없음. 스테이징 없음. 운영 확인은 `/api/health` 하나, 전환 뒤 실패해도 자동으로 되돌리지 않음.

## 단계와 브랜치 (이미지 → One Blog 브랜치 규칙)

| 단계 | 언제 | 하는 일 | 목표 시간 |
|---|---|---|---|
| 1 빠른 피드백 | `feature/**`·`hotfix/**` push, `develop`·`main`으로 여는 PR | 단위 테스트(DB 없이), 정적 분석, 커버리지 | 5분 안 |
| 2 통합 확인 | `develop`·`main` push(= merge) | 전체 테스트, 통합 테스트(MySQL), jar·Docker 만들기와 실행 확인 | 지금과 같음 |
| 3 스테이징 | 만들지 않음 (Q1) | — | — |
| 4 운영 | `main`에서 버전을 올려 배포할 때 | 운영 스모크, 실패 시 자동 되돌리기 (카나리 없음, Q2) | 지금과 비슷 |

## 사용자 시나리오

### US1 - 기능 브랜치에서 빠른 피드백 (P1)

개발자가 `feature/*`에 push하면 몇 분 안에 단위 테스트·정적 분석 결과를 받는다.

**Why**: 지금은 문구 한 줄을 고쳐도 MySQL을 띄워 전체 테스트와 Docker 빌드까지 돈다. 작은 변경마다 오래 기다린다.

**Independent Test**: `feature/*`에 push했을 때 MySQL·통합 테스트·Docker 단계 없이 1단계만 돌고 5분 안에 끝나는지 본다.

1. **Given** `feature/comments`에 push, **When** CI가 돌면, **Then** 단위 테스트, 정적 분석, 커버리지만 돌고 통합 테스트·jar·Docker 확인은 돌지 않는다.
2. **Given** `develop`으로 PR, **When** CI가 돌면, **Then** 1단계 결과가 PR 화면에 보이고, 정적 분석이 찾은 새 문제와 커버리지가 PR에 요약된다.
3. **Given** 단위 테스트 실패, **When** 1단계가 끝나면, **Then** 실패 원인이 지금처럼 Actions 화면에 표시된다.

### US2 - 합칠 때 통합 확인 (P1)

`develop`·`main`에 merge되면 지금 CI가 하던 전체 확인이 돈다.

**Why**: 통합 테스트·배포 파일 확인은 비싸지만 배포 전에는 꼭 필요하다. 배포(`main`)는 2단계 성공 뒤에만 진행된다(지금 규칙 유지).

1. **Given** `develop`에 merge, **When** CI가 돌면, **Then** 전체 테스트 → jar 실행 확인 → Docker 실행 확인이 지금과 같이 돈다.
2. **Given** `main`에 merge, **When** 2단계가 성공하고 버전이 올라 있으면, **Then** 지금처럼 배포가 이어진다. 2단계가 실패하면 배포하지 않는다.
3. **Given** 기능 브랜치에서 통합 테스트를 미리 돌려 보고 싶을 때, **When** Actions에서 직접 실행(workflow_dispatch)하면, **Then** 그 브랜치에서 2단계를 돌릴 수 있다.

### US3 - 정적 분석과 커버리지 보기 (P1)

개발자가 SonarQube Cloud 화면과 PR에서 코드 문제(버그 가능성, 보안 취약점, 중복, 냄새)와 테스트가 덮는 비율을 본다.

1. **Given** 1단계, **When** 분석이 끝나면, **Then** SonarQube Cloud의 one_blog 프로젝트에 결과가 올라가고 PR에 요약 댓글이 달린다.
2. **Given** 2단계(`develop`·`main`), **When** 전체 테스트가 끝나면, **Then** 전체 테스트 기준 커버리지로 분석을 다시 올려 브랜치의 "진짜" 커버리지를 본다.
3. **Given** PR의 품질 게이트(통과 기준)가 실패, **When** merge하려 하면, **Then** merge 버튼이 막히고, PR의 SonarQube 요약에서 무엇을 고쳐야 하는지 본다. 고쳐서 push하면 다시 분석해 통과하면 merge할 수 있다 (Q3).
4. 게이트는 **새 코드(이 PR에서 바뀐 코드)** 기준이다. 지금 있는 코드의 이슈 때문에 PR이 막히지는 않는다. 기존 이슈는 따로 정리한다(후속 작업).

### US4 - 운영 배포 뒤 확인과 자동 되돌리기 (P2)

1. **Given** 프록시를 새 버전으로 바꾼 직후, **When** 운영 스모크(지금 CI의 주소 9개 확인)를 프록시 주소로 돌려 실패하면, **Then** 프록시를 옛 버전으로 자동으로 되돌리고 배포를 실패로 표시한다(옛 컨테이너가 아직 떠 있는 동안).
2. **Given** 스모크 통과, **Then** 지금처럼 옛 컨테이너를 내리고 태그를 붙인다.

### Edge Cases

- `hotfix/*`도 1단계만 돈다. `main`에 merge하면 2단계가 돌고 성공해야 배포된다(운영 버그를 서둘러 고쳐도 통합 확인을 건너뛰지 않음).
- 단위 테스트로 나눈 13개 클래스 중 나중에 DB가 필요한 테스트가 생기면: 이름 규칙(`*IntegrationTest`)으로 2단계에 간다. 이름 규칙을 readme에 적는다.
- 1단계 커버리지는 단위 테스트만 반영해 낮게 나온다(통합 테스트가 대부분이라). 숫자의 기준은 2단계 커버리지로 본다.
- SonarQube Cloud가 잠깐 안 될 때: 분석이 실패하면 게이트 결과가 없으므로 merge가 막힌다(Q3). Actions에서 다시 실행해 통과시킨다. 테스트 결과와 분석 실패는 따로 표시한다.
- 포크에서 온 PR(외부 기여)은 비밀값(SONAR_TOKEN)을 못 쓰므로 정적 분석은 건너뛰고 단위 테스트만 돈다.
- 문서·`.claude`·`.specify`만 바뀐 push는 지금처럼 CI를 건너뛴다.
- 통합 테스트 실패를 `develop`에 merge한 뒤에야 알게 될 수 있다(Shift Left의 대가). 그때는 새 feature 브랜치로 고친다. `main` 배포는 2단계가 막아 준다.

## 요구사항

- **FR-001**: CI를 1단계(빠른 피드백)와 2단계(통합 확인)로 나눈다. 1단계는 `feature/**`·`hotfix/**` push와 `develop`·`main` 대상 PR, 2단계는 `develop`·`main` push와 직접 실행에서 돈다.
- **FR-002**: 테스트를 단위(DB 없이)와 통합(`*IntegrationTest`, MySQL 필요)으로 나눠 따로 돌릴 수 있게 한다. 2단계는 둘 다 돈다.
- **FR-003**: 테스트 커버리지 보고서를 만든다(1단계: 단위, 2단계: 전체).
- **FR-004**: SonarQube Cloud로 정적 분석을 한다. 1단계에서 분석해 PR에 요약을 달고, 2단계에서 전체 커버리지로 `develop`·`main` 분석을 올린다. 토큰은 GitHub Secrets(`SONAR_TOKEN`)로만 넣는다(constitution III).
- **FR-005**: 배포 workflow는 `main`의 2단계 성공 뒤에만 돈다(지금 규칙 유지).
- **FR-006**: 운영 배포에서 프록시 전환 직후 운영 스모크를 돌리고, 실패하면 프록시를 옛 버전으로 자동으로 되돌린 뒤 배포를 실패로 끝낸다.
- **FR-007**: 3단계(스테이징)는 만들지 않는다. 카나리도 하지 않고 블루-그린을 유지한다 (Q1, Q2).
- **FR-009**: `develop`·`main` 대상 PR은 1단계(단위 테스트)와 SonarQube 품질 게이트가 모두 통과해야 merge할 수 있다 (Q3). GitHub 브랜치 보호 규칙의 필수 검사로 건다.
- **FR-008**: readme·DEPLOY.md에 단계 표, 테스트 이름 규칙, SonarQube 보는 법을 적는다. 문서 저장소 7장(구현)·8장 D-140에 기록한다.

## 성공 기준

- **SC-001**: 기능 브랜치 push의 CI가 5분 안에 끝난다(지금 전체 CI 시간의 절반 이하).
- **SC-002**: `develop`·`main` merge 뒤에는 지금과 같은 수준(테스트 265개 + jar·Docker 실행)으로 확인된다.
- **SC-003**: PR 화면에서 새로 생긴 코드 문제 수와 커버리지를 바로 본다.
- **SC-004**: 운영 스모크가 실패하는 버전을 배포하면 사용자가 그 버전을 보는 시간이 1분을 넘지 않고 옛 버전으로 돌아간다.
- **SC-005**: 기존 테스트가 하나도 빠지지 않고 둘 중 한 단계에서 돈다(단위 + 통합 = 전체).

## Assumptions

- SonarQube Cloud를 쓴다(직접 설치하는 SonarQube Server는 서버 자원·포트가 부족). 무료 플랜(비공개 기준 5만 줄까지, 지금 코드는 그 안)으로 시작한다. 저장소에 오픈소스 라이선스를 두면 OSS 무료 등급도 쓸 수 있다.
- SonarQube Cloud 가입, GitHub 조직(one-blog1) 연결, 프로젝트 만들기, 토큰을 GitHub Secrets에 넣기는 사용자가 한다(계정 작업).
- 자동 분석(Automatic Analysis) 대신 CI 분석을 쓴다. Java는 컴파일 결과와 커버리지가 필요해서다. 프로젝트를 만든 뒤 자동 분석을 끈다.
- 모니터링(느린 API·쿼리 기록)은 이전 스펙 결정대로 미룬다.
- 브랜치 보호 규칙(필수 검사 설정)은 저장소 관리자인 사용자가 GitHub 설정에서 켠다. 방법은 readme에 적는다.
- 품질 게이트 조건: 새 코드에 새 버그·취약점 0, 보안 핫스팟 모두 검토, 중복 3% 이하는 막는다. **커버리지 조건은 처음엔 게이트에서 빼고 화면에만 보인다.** 1단계 PR 커버리지는 단위 테스트만 반영해 낮게 나와(통합 테스트가 대부분), 기본 기준(새 코드 80%)으로는 거의 모든 PR이 막히기 때문이다. 2단계 전체 커버리지로 기준을 정한 뒤 게이트에 넣는다(후속 작업).

## 후속 작업 (이번에 하지 않음)

- E2E(브라우저로 화면 누르기) 테스트, 부하 테스트 (3단계를 만든다면 그 위에)
- SonarQube MCP 연결 (분석 결과가 쌓인 뒤, Mac의 Claude Code·Desktop에)
- 품질 게이트에 커버리지 조건 넣기 (2단계 전체 커버리지를 본 뒤 기준 정하기)
- 첫 분석에서 나온 기존 코드 이슈 정리
