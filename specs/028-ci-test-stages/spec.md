# Feature Specification: 배포 단계별 테스트 (CI 단계 나누기 + 정적 분석)

**Feature Branch**: `feature/ci-test-stages` | **Created**: 2026-10-15 | **Status**: Draft (Q1~Q3 답, SonarQube 서버 반영 2026-10-15)

**결정 (2026-10-15)**:
- Q1 스테이징은 만들지 않음
- Q2 블루-그린 유지 + 운영 스모크 + 자동 되돌리기(카나리 없음)
- Q3 품질 게이트를 통과하지 못하면 개선부터 한다. 받은 SonarQube 서버가 Community(PR 분석 없음, 브랜치 하나)라서 **merge 전이 아니라 merge 뒤 2단계에서 게이트를 보고, 실패하면 CI 실패 + `main` 배포를 막는다.** 고친 커밋을 새 feature 브랜치로 다시 merge한다(사용자 확인)
- SonarQube는 받은 서버 `https://s4.java21.net:9000`(SonarQube Community)의 로컬 프로젝트(GitHub 연동 없음)를 쓴다. SonarQube Cloud는 쓰지 않는다

**Input**: "매번 돌리지 말고 저 이미지대로 단계 설정해줘", "소나큐브 사용하는 법". 이미지(배포 단계마다 다른 테스트가 지킨다, Shift Left):
1 PR/커밋 — 단위 테스트·정적 분석(SonarQube)·커버리지 → 2 main 머지 — 전체 테스트·통합 테스트·배포 파일 빌드 → 3 스테이징 — E2E·성능/부하·QA → 4 운영 — 스모크·카나리·모니터링/자동 롤백

**관련 요구사항**: D-117(CI), D-118·D-120(배포), D-135(블루-그린), D-136·D-137(브랜치·스펙 단위), constitution "개발 흐름"·V(단순함), 새 결정 D-140

## 지금 상태 (바꾸기 전)

- CI는 모든 push·PR에서 같은 일을 한다: 전체 테스트 265개(통합 32개 클래스 + 단위 13개 클래스) → jar 실행 확인 → Docker 실행 확인. 매번 MySQL을 띄운다.
- 정적 분석·커버리지 없음. 스테이징 없음. 운영 확인은 `/api/health` 하나, 전환 뒤 실패해도 자동으로 되돌리지 않음.

## 단계와 브랜치 (이미지 → One Blog 브랜치 규칙)

| 단계 | 언제 | 하는 일 | 목표 시간 |
|---|---|---|---|
| 0 코드 쓰는 중 | VS Code에서 파일을 고칠 때 | SonarQube for IDE를 서버 프로젝트에 연결 모드로 붙여 같은 규칙으로 검사 | 즉시 |
| 1 빠른 피드백 | `feature/**`·`hotfix/**` push, `develop`·`main`으로 여는 PR | 단위 테스트(DB 없이), 단위 테스트 커버리지 보고서 | 5분 안 |
| 2 통합 확인 | `develop`·`main` push(= merge) | 전체 테스트(통합 포함, MySQL), 전체 커버리지, SonarQube 분석 + 품질 게이트, jar·Docker 만들기와 실행 확인 | 지금 + 분석 시간 |
| 3 스테이징 | 만들지 않음 (Q1) | — | — |
| 4 운영 | `main`에서 버전을 올려 배포할 때 | 운영 스모크, 실패 시 자동 되돌리기 (카나리 없음, Q2) | 지금과 비슷 |

이미지와 다른 점: 정적 분석이 1단계(PR)가 아니라 0단계(IDE)와 2단계(merge 뒤)에 있다. 서버가 Community라 PR 코드를 따로 분석할 수 없기 때문이다(PR을 분석해 올리면 `develop` 결과를 덮어씀).

## 사용자 시나리오

### US1 - 기능 브랜치에서 빠른 피드백 (P1)

개발자가 `feature/*`에 push하면 몇 분 안에 단위 테스트 결과를 받는다.

**Why**: 지금은 문구 한 줄을 고쳐도 MySQL을 띄워 전체 테스트와 Docker 빌드까지 돈다. 작은 변경마다 오래 기다린다.

**Independent Test**: `feature/*`에 push했을 때 MySQL·통합 테스트·Docker 단계 없이 1단계만 돌고 5분 안에 끝나는지 본다.

1. **Given** `feature/comments`에 push, **When** CI가 돌면, **Then** 단위 테스트와 커버리지 보고서만 만들고 통합 테스트·SonarQube·jar·Docker 확인은 돌지 않는다.
2. **Given** `develop`으로 PR, **When** CI가 돌면, **Then** 1단계 결과가 PR 검사로 보이고, 실패하면 merge할 수 없다(브랜치 보호 필수 검사).
3. **Given** 단위 테스트 실패, **When** 1단계가 끝나면, **Then** 실패 원인이 지금처럼 Actions 화면에 표시된다.

### US2 - 합칠 때 통합 확인 (P1)

`develop`·`main`에 merge되면 지금 CI가 하던 전체 확인에 정적 분석이 더해져 돈다.

**Why**: 통합 테스트·배포 파일 확인은 비싸지만 배포 전에는 꼭 필요하다. 배포(`main`)는 2단계 성공 뒤에만 진행된다(지금 규칙 유지).

1. **Given** `develop`에 merge, **When** CI가 돌면, **Then** 전체 테스트 → SonarQube 분석·품질 게이트 → jar 실행 확인 → Docker 실행 확인이 돈다.
2. **Given** `main`에 merge, **When** 2단계가 성공하고 버전이 올라 있으면, **Then** 지금처럼 배포가 이어진다. 2단계(품질 게이트 포함)가 실패하면 배포하지 않는다.
3. **Given** 기능 브랜치에서 통합 테스트를 미리 돌려 보고 싶을 때, **When** Actions에서 직접 실행(workflow_dispatch)하면, **Then** 그 브랜치에서 테스트·jar·Docker 확인을 돌릴 수 있다. 이때 SonarQube에는 올리지 않는다(`develop` 결과를 덮어쓰지 않게).

### US3 - 정적 분석과 품질 게이트 (P1)

개발자가 SonarQube 서버 화면에서 코드 문제(버그 가능성, 보안 취약점, 중복, 냄새)와 테스트가 덮는 비율을 보고, 기준을 못 넘으면 고친다.

1. **Given** `develop`·`main`의 2단계, **When** 전체 테스트가 끝나면, **Then** 전체 테스트 커버리지와 함께 분석이 서버의 One Blog 프로젝트에 올라간다.
2. **Given** 품질 게이트 실패, **When** 분석이 끝나면, **Then** 2단계가 실패로 끝나고 Actions 화면에 게이트 실패와 SonarQube 화면 주소가 보인다. `main`이면 배포하지 않는다 (Q3).
3. **Given** 게이트 실패, **When** 개발자가 새 feature 브랜치에서 고쳐 다시 merge하면, **Then** 다시 분석해 통과하면 2단계가 성공한다. `develop`이 게이트를 통과하기 전에는 버전을 올려 배포하지 않는다.
4. 게이트는 서버의 **새 코드** 기준(서버 설정)으로 본다. 지금 있는 코드의 이슈 때문에 바로 실패하지는 않게 첫 분석을 기준점으로 둔다(plan에서 방법 확인).
5. **Given** VS Code 연결 모드, **When** 코드를 고치면, **Then** 서버와 같은 규칙의 문제가 편집기에 바로 표시된다(0단계).

### US4 - 운영 배포 뒤 확인과 자동 되돌리기 (P2)

1. **Given** 프록시를 새 버전으로 바꾼 직후, **When** 운영 스모크(지금 CI의 주소 9개 확인)를 프록시 주소로 돌려 실패하면, **Then** 프록시를 옛 버전으로 자동으로 되돌리고 배포를 실패로 표시한다(옛 컨테이너가 아직 떠 있는 동안).
2. **Given** 스모크 통과, **Then** 지금처럼 옛 컨테이너를 내리고 태그를 붙인다.

### Edge Cases

- `hotfix/*`도 1단계만 돈다. `main`에 merge하면 2단계(게이트 포함)가 돌고 성공해야 배포된다. hotfix가 게이트에 걸리면 고치는 커밋을 더해야 배포된다.
- `develop`과 `main`이 서버의 프로젝트 하나(브랜치 하나)를 함께 쓴다. 분석은 마지막에 올린 것이 남는다. `main`은 `develop`을 merge한 것이라 내용이 같아 문제가 적다. hotfix가 `main`에 먼저 들어가면 잠깐 어긋나지만 `develop`에도 합치면서 맞춰진다.
- 같은 프로젝트에 분석이 동시에 둘 올라가지 않게 2단계 분석은 한 번에 하나씩 돈다.
- 단위 테스트로 나눈 13개 클래스 중 나중에 DB가 필요한 테스트가 생기면: 이름 규칙(`*IntegrationTest`)으로 2단계에 간다. 이름 규칙을 readme에 적는다.
- SonarQube 서버가 꺼져 있거나 닿지 않을 때: 게이트 결과가 없으므로 2단계가 실패한다(배포 안 됨). 서버가 돌아오면 Actions에서 다시 실행한다. 테스트 실패와 분석 실패는 따로 표시한다.
- 서버가 GitHub Actions(인터넷)에서 닿지 않으면 이 방식 전체가 안 된다: 구현 첫 작업에서 Actions로 연결을 확인한다.
- 문서·`.claude`·`.specify`만 바뀐 push는 지금처럼 CI를 건너뛴다.
- 통합 테스트 실패·게이트 실패를 `develop`에 merge한 뒤에야 알게 될 수 있다(Shift Left의 대가). 그때는 새 feature 브랜치로 고친다. `main` 배포는 2단계가 막아 준다.

## 요구사항

- **FR-001**: CI를 1단계(빠른 피드백)와 2단계(통합 확인)로 나눈다. 1단계는 `feature/**`·`hotfix/**` push와 `develop`·`main` 대상 PR, 2단계는 `develop`·`main` push와 직접 실행에서 돈다.
- **FR-002**: 테스트를 단위(DB 없이)와 통합(`*IntegrationTest`, MySQL 필요)으로 나눠 따로 돌릴 수 있게 한다. 2단계는 둘 다 돈다.
- **FR-003**: 테스트 커버리지 보고서를 만든다(1단계: 단위, 2단계: 전체). 1단계 보고서는 Actions 결과로 내려받을 수 있다.
- **FR-004**: 2단계(`develop`·`main` push)에서 전체 커버리지와 함께 SonarQube 서버(`https://s4.java21.net:9000`)로 분석을 올리고 품질 게이트 결과를 기다린다. 실패하면 2단계를 실패로 끝낸다. 토큰과 서버 주소는 GitHub Secrets(`SONAR_TOKEN`, `SONAR_HOST_URL`)로만 넣는다(constitution III). 프로젝트 키는 설정 파일에 적는다.
- **FR-005**: 배포 workflow는 `main`의 2단계 성공(품질 게이트 포함) 뒤에만 돈다.
- **FR-006**: 운영 배포에서 프록시 전환 직후 운영 스모크를 돌리고, 실패하면 프록시를 옛 버전으로 자동으로 되돌린 뒤 배포를 실패로 끝낸다.
- **FR-007**: 3단계(스테이징)는 만들지 않는다. 카나리도 하지 않고 블루-그린을 유지한다 (Q1, Q2).
- **FR-008**: readme·DEPLOY.md에 단계 표, 테스트 이름 규칙, SonarQube 보는 법(서버 화면, VS Code 연결 모드), 게이트 실패 시 고치는 순서를 적는다. 문서 저장소 7장(구현)·8장 D-140에 기록한다.
- **FR-009**: `develop`·`main` 대상 PR은 1단계(단위 테스트)가 통과해야 merge할 수 있다. GitHub 브랜치 보호 규칙의 필수 검사로 건다.

## 성공 기준

- **SC-001**: 기능 브랜치 push의 CI가 5분 안에 끝난다(지금 전체 CI 시간의 절반 이하).
- **SC-002**: `develop`·`main` merge 뒤에는 지금과 같은 수준(테스트 265개 + jar·Docker 실행)에 정적 분석이 더해져 확인된다.
- **SC-003**: 품질 게이트를 못 넘는 코드가 `main`에 들어가면 배포되지 않는다.
- **SC-004**: 운영 스모크가 실패하는 버전을 배포하면 사용자가 그 버전을 보는 시간이 1분을 넘지 않고 옛 버전으로 돌아간다.
- **SC-005**: 기존 테스트가 하나도 빠지지 않고 둘 중 한 단계에서 돈다(단위 + 통합 = 전체).

## Assumptions

- SonarQube 서버는 받은 공용 서버다. 사용자는 일반 계정이라 서버 설정(GitHub 연동, 품질 게이트 조건 바꾸기)은 할 수 없다. 게이트 조건은 서버 기본값(보통 "Sonar way": 새 코드의 신뢰성·보안·유지보수 등급, 보안 핫스팟 검토, 중복, 커버리지)을 그대로 따른다. 새 코드 커버리지 조건이 있으면 2단계의 **전체** 커버리지로 판단되므로 통합 테스트가 있는 기능은 넘을 가능성이 높다. 계속 막히면 관리자에게 조건 조정을 부탁하거나 테스트를 더한다.
- 사용자가 할 일: 서버에서 토큰 만들기(가능하면 이 프로젝트 전용 분석 토큰), GitHub Secrets에 `SONAR_TOKEN`·`SONAR_HOST_URL` 넣기, Project key 알려 주기, 브랜치 보호 규칙 켜기, VS Code 연결 모드 설정(선택).
- 서버가 GitHub Actions에서 닿는다고 가정한다(주소가 공개 도메인). 이 작업 환경에서는 확인할 수 없어 구현 첫 단계에서 Actions로 확인한다.
- 모니터링(느린 API·쿼리 기록)은 이전 스펙 결정대로 미룬다.

## 후속 작업 (이번에 하지 않음)

- E2E(브라우저로 화면 누르기) 테스트, 부하 테스트 (3단계를 만든다면 그 위에)
- PR 단계 정적 분석 (서버가 PR 분석을 지원하는 에디션이 되거나 SonarQube Cloud로 옮기면)
- SonarQube MCP 연결 (분석 결과가 쌓인 뒤, Mac의 Claude Code·Desktop에. Community 서버도 지원)
- 첫 분석에서 나온 기존 코드 이슈 정리
