## User Scenarios & Testing *(mandatory)*

### User Story 1 - 이메일 인증으로 회원가입하기 (Priority: P1)

방문자가 메인블로그에서 회원가입을 시작한다. ① 이메일을 입력하고 메일로 받은 6자리 인증번호를 입력해 이메일을 인증한다. ② 비밀번호를 두 번 입력한다. ③ 이름, 닉네임, 전화번호를 입력하고 이용약관과 개인정보 수집·이용에 동의한다. 세 단계를 모두 마쳐야 계정이 만들어진다.

**Why this priority**: 계정이 없으면 블로그 생성·참여·글쓰기 등 다른 모든 기능을 쓸 수 없다. 플랫폼의 첫 관문이다 (constitution II 1단계).

**Independent Test**: 새 이메일로 세 단계를 끝까지 진행해 계정이 만들어지고, 같은 이메일·닉네임으로 다시 가입할 수 없는지 확인한다. 로그인 기능 없이도 계정 생성 여부를 확인할 수 있다.

**Acceptance Scenarios**:

1. **Given** 가입되지 않은 이메일, **When** 방문자가 이메일을 입력하고 인증번호 받기를 누르면, **Then** 화면에 "인증번호를 보냈습니다"가 보이고 그 이메일로 6자리 인증번호가 발송된다.
2. **Given** 이미 가입된 이메일, **When** 방문자가 그 이메일로 인증번호 받기를 누르면, **Then** 화면에는 1번과 똑같이 "인증번호를 보냈습니다"가 보이고, 그 이메일로는 인증번호 대신 "이미 가입된 이메일입니다" 안내 메일이 발송된다 (D-28).
3. **Given** 인증번호를 받은 상태, **When** 10분 안에 맞는 번호를 입력하면, **Then** 이메일 인증이 완료되고 ② 비밀번호 단계로 넘어간다.
4. **Given** 인증번호를 받은 상태, **When** 틀린 번호를 입력하면, **Then** 틀렸다는 안내와 남은 시도 횟수가 보이고, 5번째로 틀리면 그 번호는 무효가 되어 다시 받아야 한다.
5. **Given** 인증번호를 받은 지 1분이 지나지 않은 상태, **When** 다시 보내기를 누르면, **Then** 발송되지 않고 다시 보낼 수 있을 때까지 남은 시간이 보인다.
6. **Given** 1분이 지난 상태, **When** 다시 보내기를 누르면, **Then** 새 인증번호가 발송되고 이전 번호는 무효가 된다.
7. **Given** 이메일 인증을 마친 상태, **When** 규칙(8~15자, 영문·숫자·특수문자 모두 포함)에 맞는 비밀번호를 두 번 똑같이 입력하면, **Then** ③ 단계로 넘어간다. 규칙에 맞지 않거나 두 입력이 다르면 이유가 보이고 넘어가지 않는다.
8. **Given** ③ 단계, **When** 이름·닉네임·전화번호를 입력하고 두 필수 동의에 체크한 뒤 가입하기를 누르면, **Then** 계정이 만들어지고 가입 완료 화면(로그인 화면으로 이동)이 보인다.
9. **Given** ③ 단계, **When** 이미 쓰이는 닉네임이나 예약어(관리자, admin, 운영자, 탈퇴한 회원)를 입력하면, **Then** 사용할 수 없다는 안내가 보이고 가입되지 않는다.
10. **Given** ③ 단계, **When** 필수 동의 중 하나라도 체크하지 않으면, **Then** 가입하기를 진행할 수 없다.

### User Story 2 - 이메일·비밀번호로 로그인하고 로그아웃하기 (Priority: P2)

회원이 이메일과 비밀번호로 로그인한다. 로그인 상태는 메인블로그와 모든 개별 블로그에서 똑같이 유지된다. 회원은 언제든 로그아웃 버튼으로 즉시 로그아웃할 수 있다.

**Why this priority**: 가입한 회원이 자기 계정으로 활동하려면 로그인이 필요하다. 가입(P1) 다음으로 중요하다.

**Independent Test**: 가입된 계정으로 로그인해 로그인 상태가 보이는지, 로그아웃 후 로그인이 필요한 화면에 다시 들어갈 수 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 가입된 회원, **When** 맞는 이메일과 비밀번호로 로그인하면, **Then** 로그인 상태가 되고 상단 메뉴에 내 닉네임이 보인다.
2. **Given** 가입된 회원, **When** 이메일 대소문자를 다르게 입력해도(예: A@x.com), **Then** 같은 계정으로 로그인된다 (6.5).
3. **Given** 로그인 화면, **When** 이메일이 없거나 비밀번호가 틀리면, **Then** 어느 쪽이 틀렸는지 구분하지 않는 같은 문구("이메일 또는 비밀번호가 올바르지 않습니다")가 보인다.
4. **Given** 로그인한 회원, **When** 로그아웃 버튼을 누르면, **Then** 즉시 로그아웃되고 메인 화면으로 이동하며, 그 로그인으로 다시 로그인 상태를 되살릴 수 없다 (USR-04).
5. **Given** 로그인한 회원, **When** 메인블로그에서 개별 블로그 주소(/blog/{주소})로 이동하면, **Then** 다시 로그인하지 않아도 로그인 상태가 유지된다 (USR-03).

### User Story 3 - "로그인 유지" 선택과 자동 로그아웃 (Priority: P3)

로그인 화면의 "로그인 유지" 체크박스로 회원이 로그인 유지 방식을 고른다. 체크하지 않으면 브라우저를 닫거나 30분 동안 활동이 없을 때 로그아웃되고, 체크하면 14일 동안 로그인이 유지된다.

**Why this priority**: 공용 PC에서 로그인이 남지 않게 하는 보안 규칙이지만, 기본 로그인(P2)이 먼저 있어야 의미가 있다.

**Independent Test**: 체크 여부별로 로그인한 뒤 브라우저 종료, 30분 무활동, 14일 경과 상황에서 로그인 상태가 규칙대로 바뀌는지 확인한다.

**Acceptance Scenarios**:

1. **Given** "로그인 유지"를 체크하지 않고 로그인한 회원, **When** 브라우저를 완전히 닫았다가 다시 열면, **Then** 로그아웃되어 있다.
2. **Given** "로그인 유지"를 체크하지 않고 로그인한 회원, **When** 30분 동안 직접 한 행동(페이지 이동, 버튼 클릭 등)으로 서버에 요청을 보내지 않으면, **Then** 로그아웃된다.
3. **Given** "로그인 유지"를 체크하지 않고 로그인한 회원, **When** 30분이 되기 전에 직접 한 행동으로 요청을 보내면, **Then** 30분이 그 시점부터 다시 시작된다.
4. **Given** "로그인 유지"를 체크하지 않고 로그인한 회원, **When** 화면이 저절로 보내는 요청만 있고 직접 한 행동은 없으면, **Then** 30분은 연장되지 않는다 (D-62).
5. **Given** "로그인 유지"를 체크하고 로그인한 회원, **When** 브라우저를 닫았다가 14일 안에 다시 열면, **Then** 로그인 상태가 유지된다.
6. **Given** "로그인 유지"를 체크하고 로그인한 회원, **When** 14일이 지나면, **Then** 로그아웃되어 다시 로그인해야 한다.

---

### Edge Cases

- 인증번호를 받은 뒤 10분이 지나 입력하면 만료 안내가 보이고 새 번호를 받아야 한다.
- 화면 단계를 건너뛰고 ③ 단계 가입 요청을 직접 보내면, 서버가 이 이메일의 인증 완료 여부를 다시 확인해 거부한다 (USR-02 구현 순서 5).
- 이메일 인증 후 오랫동안 ②·③ 단계를 마치지 않으면 인증이 만료되어 처음부터 다시 해야 한다.
- 두 사람이 거의 동시에 같은 닉네임으로 가입하면 한 명만 성공하고 다른 한 명에게는 사용할 수 없다는 안내가 보인다.
- 인증 대기 중에 다른 사람이 같은 이메일로 먼저 가입을 끝내면, 늦은 쪽의 가입은 "이미 가입된 이메일" 대신 일반 실패 안내로 끝나고 다시 시작해야 한다(가입 여부를 드러내지 않음).
- 로그아웃 후 브라우저의 뒤로 가기로 로그인이 필요한 화면을 열어도 데이터가 보이지 않고 로그인 화면으로 이동한다.
- 한 회원이 여러 기기에서 로그인하면 기기마다 로그인이 따로 유지되고, 한 기기의 로그아웃은 그 기기만 로그아웃한다.
- 이름·닉네임·전화번호 앞뒤 공백은 제거하고 저장하며, 전화번호는 하이픈 등을 빼고 숫자만 저장한다.
- 관리자 계정(이메일 없음)은 이 화면으로 로그인할 수 없다 (관리자 로그인은 후속 작업).

## Requirements *(mandatory)*

### Functional Requirements

**회원가입 (USR-01)**

- **FR-001**: 시스템은 ① 이메일 인증 → ② 비밀번호 입력 → ③ 이름·닉네임·전화번호 입력과 동의 순서의 가입 절차를 제공해야 하며, 세 단계를 모두 마쳐야 계정을 만든다.
- **FR-002**: 시스템은 이메일을 소문자로 바꿔 저장하고, 이미 가입된 이메일로는 계정을 만들지 않아야 한다 (6.5).
- **FR-003**: 시스템은 닉네임을 2~12자 한글·영문·숫자로 제한하고, 중복과 예약어(관리자, admin, 운영자, 탈퇴한 회원)를 거부해야 한다 (6.5). 예약어 비교는 영문 대소문자를 구분하지 않는다.
- **FR-004**: 시스템은 전화번호를 숫자만 저장하고, 1차에는 같은 번호로 여러 계정을 허용해야 한다 (USR-01, D-24).
- **FR-005**: 시스템은 ③ 단계에서 [필수] 이용약관, [필수] 개인정보 수집·이용 동의를 각각 받고, 두 동의의 시각을 저장해야 한다 (4.6).
- **FR-006**: 시스템은 가입 완료 요청을 받을 때마다 그 이메일의 인증 완료 여부를 서버에서 다시 확인해야 한다 (USR-02).

**이메일 인증 (USR-02)**

- **FR-007**: 시스템은 입력한 이메일로 6자리 숫자 인증번호를 보내야 한다.
- **FR-008**: 인증번호는 발송 10분 뒤 만료되고, 5번 틀리면 무효가 되어야 한다 (USR-02, D-42).
- **FR-009**: 다시 보내기는 같은 이메일에 1분에 한 번만 허용하고, 다시 보내면 이전 인증번호는 무효가 되어야 한다.
- **FR-010**: 이미 가입된 이메일이면 화면에는 가입되지 않은 이메일과 똑같은 문구를 보여주고, 그 이메일로 인증번호 대신 "이미 가입된 이메일입니다" 안내 메일을 보내야 한다 (D-28).
- **FR-011**: 시스템은 인증번호를 원문 그대로 저장하지 않아야 한다 (민감 정보 저장 규칙).

**비밀번호 (SEC-01, SEC-02)**

- **FR-012**: 비밀번호는 8~15자이고 영문·숫자·특수문자를 모두 포함해야 하며, 대소문자를 구분한다 (SEC-02, 6.7). 화면과 서버 모두에서 검사한다.
- **FR-013**: 시스템은 비밀번호를 단방향 해시로만 저장하고 원문을 어디에도 남기지 않아야 한다 (SEC-01).

**로그인·로그인 유지 (USR-03, SEC-04)**

- **FR-014**: 회원은 이메일과 비밀번호로 로그인할 수 있어야 하며, 로그인 상태는 메인블로그와 모든 개별 블로그에서 유지되어야 한다 (USR-03).
- **FR-015**: 로그인 실패 시 이메일과 비밀번호 중 무엇이 틀렸는지 구분하지 않는 같은 문구를 보여야 한다.
- **FR-016**: 로그인 정보는 화면의 스크립트가 읽을 수 없는 방식으로 브라우저에 보관하고, 보안 연결로만 주고받아야 한다 (SEC-04, SEC-10).
- **FR-017**: 로그인 화면에 "로그인 유지" 체크박스가 있어야 한다. 체크하지 않으면 브라우저를 닫거나 30분 동안 직접 한 행동이 없을 때 로그아웃되고, 체크하면 14일 동안 유지되어야 한다 (SEC-04, D-61).
- **FR-018**: 30분 무활동은 사용자가 직접 한 행동으로 서버에 간 요청마다 다시 시작하고, 화면이 저절로 보내는 요청은 활동으로 세지 않아야 한다 (D-62).
- **FR-019**: 시스템은 로그인을 이어 주는 정보를 서버에 저장해, 서버가 언제든 그 로그인을 끊을 수 있어야 한다 (D-82).
- **FR-020**: 회원의 역할·상태 확인은 브라우저에 보관된 정보만 믿지 않고 요청마다 서버의 저장된 정보로 확인해야 한다 (SEC-07, constitution III).

**로그아웃 (USR-04)**

- **FR-021**: 로그아웃하면 서버에서 그 기기의 로그인을 끊고, 브라우저에 보관된 로그인 정보를 지운 뒤 메인 화면으로 이동해야 한다 (USR-04).

**공통**

- **FR-022**: 상태를 바꾸는 모든 요청(가입, 인증번호 발송·확인, 로그인, 로그아웃)은 위조 요청 방지 검사를 거쳐야 한다 (SEC-10).
- **FR-023**: 사용자 입력은 화면에 표시할 때 문자 그대로 보여야 하며, 실행 가능한 코드로 해석되지 않아야 한다 (SEC-06).

### Key Entities *(include if feature involves data)*

- **회원(users)**: 이메일(로그인 아이디), 비밀번호 해시, 이름, 닉네임, 전화번호, 권한(USER/ADMIN), 상태, 이용약관·개인정보 동의 시각, 가입·수정 시각. Crowfoot ERD의 `users`를 따른다.
- **이메일 인증번호(verification_codes)**: 이메일, 용도(가입), 인증번호 해시, 틀린 횟수, 만료 시각, 인증 완료 시각, 발송 시각. 회원이 만들어지기 전 단계라 이메일로 묶는다.
- **로그인 유지 정보(refresh_tokens)**: 회원, 토큰 해시, 로그인 유지 여부, 마지막 활동 시각, 만료 시각, 폐기 시각. 한 회원이 기기마다 하나씩 가질 수 있다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 처음 온 방문자가 가입 세 단계를 3분 안에 끝낼 수 있다 (메일 수신 대기 시간 제외).
- **SC-002**: 인증번호 메일은 요청 후 1분 안에 받은편지함에 도착한다.
- **SC-003**: 가입·로그인 화면의 응답은 2초 안에 온다 (4.2 성능 목표).
- **SC-004**: 가입된 이메일과 가입되지 않은 이메일로 인증번호를 요청했을 때 화면 문구와 응답에 차이가 없어, 화면만 보고 가입 여부를 알아낼 수 없다.
- **SC-005**: 로그아웃한 뒤에는 그 기기의 이전 로그인 정보로 로그인이 필요한 기능을 하나도 쓸 수 없다.
- **SC-006**: 저장된 데이터 어디에서도 비밀번호와 인증번호의 원문을 찾을 수 없다.
- **SC-007**: "로그인 유지" 미체크 시 30분 무활동 후, 체크 시 14일 후 로그아웃이 100% 일어난다.

## Assumptions

- 가입 완료 후에는 자동 로그인하지 않고 로그인 화면으로 이동한다.
- 이메일 인증을 마친 뒤 ②·③ 단계를 끝내야 하는 시간은 인증 완료 시점부터 30분으로 한다. 지나면 처음부터 다시 한다.
- 이름은 앞뒤 공백을 뺀 1~50자, 전화번호는 숫자 10~11자리(휴대전화 번호)로 받는다.
- 인증번호 발송·확인 요청 횟수 제한(IP별)은 이번 범위가 아니다. 다시 보내기 1분 제한과 5회 오답 무효만 적용한다.
- 메일 발송 수단(Gmail SMTP, D-69)의 발송 계정과 비밀번호는 저장소 밖 설정으로 준비되어 있다.
- 글쓰기 화면의 입력 중 로그인 연장과 만료 5분 전 연장 안내(SEC-04)는 글쓰기 기능(BRD-01)을 만들 때 함께 구현한다.
- 화면은 PC와 모바일 모두에서 쓸 수 있어야 한다 (4.2).
