# Feature Specification: SonarQube 첫 분석 정리 (B 범위)

**Feature Branch**: `feature/sonar-cleanup` | **Created**: 2026-10-16 | **Status**: Draft (specify 확인 대기)

**Input**: SonarQube 서버(`one-blog`) 첫 분석 결과(이슈 202, 핫스팟 31, 지표)를 받아 "부족한 점들 수정". 범위는 사용자가 B로 정함(2026-10-16): 버그·취약점 전부 + 복잡한 메서드 + 트랜잭션 self-call + 빈 블록. 대상 목록은 [issues.md](issues.md).

**관련 요구사항**: D-140(정적 분석·품질 게이트), constitution III(보안 기준선)·V(단순함), SEC-01·SEC-03(로그인), SCL-03(배치), 새 결정 D-141

## 지금 상태 (0.20 분석)

| 지표 | 값 | 원인 |
|---|---|---|
| 보안 등급 | **E** | 취약점 1개: 로그인 시간 맞추기용 가짜 해시의 원문 문자열을 "유출된 비밀번호"로 봄 (`AuthService`) |
| 신뢰성 등급 | **E** | BLOCKER 버그 1개(`TagService` 트랜잭션 self-call) + MAJOR 버그 32개 |
| 유지보수 등급 | A | 냄새 168개 |
| 커버리지 / 중복 | 82.9% / 0.4% | |
| 보안 핫스팟 | 31개 검토 전 | SQL 조각 이어 붙이기 24, 비밀번호 의심 3, 정규식 3, 난수 1 |

## 바뀌지 않는 것

- **사용자가 보는 동작·API 응답·DB 구조는 바꾸지 않는다.** 리팩터링과 방어 코드 정리만 한다. 마이그레이션·ERD 변경 없음.
- 기존 테스트(378개 + E2E 8개)는 고치지 않고 그대로 통과해야 한다. 테스트가 동작 변화를 잡으면 코드를 되돌린다.
- B 범위 밖의 냄새(같은 문자열 반복 56, 테스트 assert 문법, 정규식 문법, 삼항 중첩 등 약 145개)는 이번에 고치지 않는다(후속 작업).

## 사용자 시나리오

### US1 - 보안·신뢰성 등급 E → A (P1)

운영자(본인)가 SonarQube 화면에서 보안·신뢰성 등급이 A인 것을 본다.

**Why**: 등급이 E면 진짜 위험이 생겨도 눈에 띄지 않는다. 지금 E의 원인은 실제 위험이 거의 없는 두 줄과 정리되지 않은 버그 경고다.

**Independent Test**: 이 브랜치를 merge한 뒤 `develop` 분석에서 보안 A, 신뢰성 A, 미처리 버그·취약점 0.

1. **Given** 취약점(가짜 해시 문자열), **When** 고치면, **Then** 서버 시작 때 무작위 값으로 가짜 해시를 만들고, 없는 이메일과 틀린 비밀번호의 로그인 응답 시간이 지금처럼 비슷하다(SEC-01, 계정 존재 여부를 시간으로 알 수 없게).
2. **Given** 버그 34개, **When** 각 항목을 판단하면, **Then** 실제로 고칠 것은 코드로 고치고, 분석기가 잘못 본 것(예: `TransactionTemplate.execute`가 null일 수 있는데 "항상 false"로 본 조건)은 코드를 그대로 두고 서버에서 "오탐"으로 표시할 근거를 남긴다.
3. null 가능성 경고(19개) 중 `COUNT(*)` 결과를 바로 `long`에 넣는 곳은 null이면 서버 오류(500)가 나는 형태라 공통 도우미로 0을 돌려주게 고친다.

### US2 - 복잡한 코드 정리 (P2)

개발자가 읽고 고치기 어려운 메서드를 작은 메서드로 나눈다.

**Why**: 인지 복잡도 15를 넘는 메서드 10개가 이미지 메타데이터 제거·알림·글 본문 처리·배너·로그인처럼 민감한 곳에 있다. 다음에 손댈 때 실수하기 쉽다.

1. **Given** 복잡도 초과 메서드 10개(`ImageMetadataStripper` 34·16, `NotificationQueryService` 30, `BannerAdminService` 23, `MarkdownRenderer` 22, `CommentService` 20, `AuthService` 18, `AccountService` 17, `BlogJoinService` 16, 긴 메서드 1), **When** 나누면, **Then** 각 메서드가 15 이하이고 동작은 같다(기존 테스트 통과).
2. 나눈 메서드에는 하는 일을 한 줄 주석으로 남긴다(프로젝트 관례).

### US3 - 트랜잭션·빈 블록 정리 (P3)

1. **Given** 같은 클래스 안에서 `@Transactional` 메서드를 부르는 곳 11개, **When** 확인하면, **Then** 모두 바깥 메서드에 이미 트랜잭션이 있어 동작 문제는 없음을 확인하고, 안쪽 메서드의 쓸모없는 어노테이션을 정리하거나 구조를 바꿔 경고를 없앤다. 트랜잭션 범위(읽기 전용 여부, 롤백 규칙)는 지금과 같게 유지한다.
2. **Given** 신고 처리의 빈 `case "NO_ISSUE" -> {}` 2곳, **When** 고치면, **Then** "문제없음은 신고만 닫는다"는 의도가 코드에 드러나게 한다.

### US4 - 보안 핫스팟 검토 (P1)

1. **Given** 핫스팟 31개, **When** 검토하면, **Then** 항목마다 판단(안전/수정)과 근거를 문서로 남기고, 사용자가 그 근거로 서버에서 "Safe"(또는 수정)로 표시한다.
2. SQL 조각 24개: 이어 붙이는 조각이 코드에 고정된 문자열이거나 정해진 값 중에서 고른 것이고, 사용자 값은 모두 바인딩되는지 하나씩 확인해 근거에 적는다.
3. 정규식 3개(끝 `/`·문장부호 지우기): 정규식 없이 같은 결과를 내도록 바꿔 핫스팟을 없앤다.

### Edge Cases

- 분석 줄 번호는 0.20 기준이라 029(테스트 보강, `HttpVideoThumbnailFetcher`·배치 수정) merge 뒤 위치가 조금 다를 수 있다. 규칙과 메서드 이름으로 찾는다.
- 리팩터링이 테스트로는 안 잡히는 동작을 바꿀 수 있다: 복잡도 정리는 메서드를 옮기기만 하고 조건 순서·예외·로그 문구를 바꾸지 않는다.
- 오탐 표시는 서버 화면에서만 할 수 있다(사용자 계정). 이 브랜치에는 근거 목록만 둔다.
- merge 뒤 첫 분석에서 새 코드(이번 변경)에 새 이슈가 생기면 품질 게이트가 실패한다: merge 전에 VS Code SonarQube(연결 모드)나 규칙을 보며 새 이슈를 만들지 않게 한다.

## 요구사항

- **FR-001**: `AuthService`의 가짜 해시를 서버 시작 때 무작위 값으로 만든다. 문자열 원문을 코드에 두지 않는다.
- **FR-002**: `TagService.findBlogTags(Long)`의 트랜잭션 경고(BLOCKER)를 없앤다.
- **FR-003**: 버그 34개(issues.md B1~B34)를 하나씩 `수정` 또는 `오탐`으로 판단하고, `수정`은 동작을 바꾸지 않고 고친다. `COUNT(*)` 결과는 null이면 0으로 다루는 공통 도우미를 쓴다.
- **FR-004**: 인지 복잡도 초과 메서드 10개(S 목록의 S3776·S6541)를 15 이하로 나눈다.
- **FR-005**: 트랜잭션 self-call 11개와 빈 블록 2개(S 목록)를 정리한다. 트랜잭션 범위는 바꾸지 않는다.
- **FR-006**: 핫스팟 31개(H1~H31)의 판단과 근거를 `specs/030-sonar-cleanup/hotspots.md`에 남긴다. 정규식 3개는 코드로 없앤다.
- **FR-007**: 오탐·고치지 않음 목록과 서버 표시 방법을 문서로 남긴다(사용자가 표시).
- **FR-008**: 문서 저장소 8장에 D-141(정적 분석 첫 정리 기준: 등급 A 유지, 오탐은 근거와 함께 서버 표시, 문자열 반복 등 기계적 냄새는 손댈 때 정리)을 남긴다.

## 성공 기준

- **SC-001**: merge 뒤 `develop` 분석에서 보안 등급 A, 신뢰성 등급 A, 유지보수 A 유지.
- **SC-002**: 미처리 버그·취약점 0(코드 수정 또는 서버 오탐 표시), 핫스팟 검토 31/31.
- **SC-003**: 인지 복잡도 15 초과 메서드 0.
- **SC-004**: 기존 테스트 378개 + E2E 8개가 그대로 통과하고, 커버리지가 82.9%보다 떨어지지 않는다.
- **SC-005**: 품질 게이트 통과(이번 변경이 새 이슈를 만들지 않음).

## Assumptions

- 서버의 오탐 표시·핫스팟 "Safe" 표시는 사용자가 한다(일반 계정에 이슈 관리 권한이 있다고 가정. 없으면 관리자에게 요청).
- 줄 번호 차이는 규칙·메서드 이름으로 찾아 맞춘다.
- 이 작업 환경은 빌드가 막혀 있어 확인은 push 뒤 CI(`unit`, 직접 실행 `full`)로 한다.

## 후속 작업 (이번에 하지 않음)

- 같은 문자열 반복(S1192) 56, 테스트 assert 문법(S5838) 17, 정규식 문법(S6353) 10, 삼항 중첩·`@RestController`·람다 등 기계적 냄새 약 145개
- 로그인 요청 제한 기록 공유(029에서 발견, SEC-03·SCL-01)
