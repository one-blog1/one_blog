# update <버전>

사용자가 `update 0.2.0`이라고 하면 아래 순서를 끝까지 진행한다. 버전 규칙과 릴리즈 노트 형식은 문서 저장소(one-blog1/one-blog_docs)의 `releases/README.md`, 배포 구조는 이 저장소의 `DEPLOY.md`(D-120)를 따른다.

버전은 사용자가 정한다. 버전 없이 `update`만 왔으면 바뀐 내용을 보고 번호(수정 → 수, 기능 → 부, 호환이 깨지는 변경 → 주)를 제안하고 물은 뒤 진행한다.

## 0. 준비 (새 채팅·새 세션에서 처음 할 때)

- 이 저장소(one-blog1/one_blog)와 문서 저장소(one-blog1/one-blog_docs) 둘 다 필요하다. 문서 저장소가 세션에 없으면 저장소 추가 도구(add_repo, push 권한)로 붙이고 clone한다.
- `gh`로 Actions 결과를 읽을 수 있는지 확인한다 (`gh run list -L 1`).

## 1. 확인 (하나라도 걸리면 멈추고 사용자에게 묻는다)

- 형식이 `숫자.숫자.숫자`인가
- 지금 버전(`build.gradle.kts`의 `version`)보다 큰가
- 코드 저장소에 태그 `v<버전>`이 아직 없는가: `git ls-remote --tags origin`
- main이고, 원격과 같고(`git pull --ff-only`), 커밋하지 않은 변경이 없는가
- 지난 버전 이후 바뀐 것이 있는가: `git fetch --tags` 후 `git log v<지난 버전>..HEAD --oneline`. 바뀐 것이 없으면 그래도 올릴지 묻는다
- 고른 자리가 바뀐 내용과 맞는가. 예: 기능을 더했는데 수 자리만 올렸으면 부 자리를 제안하고 물어본다 (사용자가 그대로 하라고 하면 그대로)

## 2. 버전 올리고 배포

1. `build.gradle.kts`의 `version = "..."`만 새 번호로 바꾼다. 다른 파일은 건드리지 않는다.
2. 커밋 `release: <버전>` 후 main에 push한다. 커밋 메시지 끝에는 세션이 알려 준 Co-Authored-By 줄을 붙인다.
3. 진행 상황을 사용자에게 한 줄로 알린다: CI → 배포 → 태그. 보통 10분 안팎.
4. 결과 확인: `gh run list -L 3` (CI, Deploy). 오래 걸리면 터미널을 붙잡고 기다리지 말고 `send_later`로 10분쯤 뒤에 다시 확인한다.
   - Deploy 성공 → 태그 `v<버전>`이 붙었는지 확인하고 다음 단계로
   - 실패 → 오류 요약(annotation)을 읽어 원인을 알리고 멈춘다. 릴리즈 노트는 쓰지 않는다. 서버는 바로 전 버전으로 되돌아가 있다

## 3. 릴리즈 노트 (문서 저장소)

1. 바뀐 것 정리: 코드 저장소 `git log v<지난 버전>..v<버전>`과 바뀐 파일. 필요하면 문서 저장소 8장 결정 기록과 specs를 함께 본다.
2. 문서 저장소에 `releases/v<버전>.md`를 만든다. 형식은 `releases/v0.1.0.md`를 따른다.
   - 첫 줄 `# One Blog <버전>`, 한 줄 요약과 날짜
   - 코드 태그, 요구사항 기준(결정 번호·기능 명세 번호)
   - 바뀐 것 (기능·화면 / 오류 수정 / 보안 / 운영·배포로 나눔, 해당 없는 묶음은 생략)
   - 알려진 제한 (그대로면 지난 버전 노트를 가리킴)
   - 블로그 공지 문구 (아래 4)
3. `releases/README.md`의 버전 목록에 한 줄을 더한다.
4. 커밋 `docs: v<버전> 릴리즈 노트` 후 push. Actions(Release notes)가 문서 저장소에 Release를 만든다. 만들어졌는지 확인한다.

## 4. 블로그 공지 문구

- 읽는 사람은 서비스 사용자. 사용자가 느끼는 변화만 쉬운 말로, 존댓말로 쓴다.
- 보안 수정은 "보안을 강화했어요" 정도로만 쓰고, 취약점 내용은 적지 않는다.
- 제목: `One Blog <버전> 업데이트 안내`
- 본문: 인사 → 바뀐 점 목록(무엇을 할 수 있게 됐는지) → 마무리 인사. 마크다운.
- 사용자에게 보이는 변화가 없는 버전이면 짧은 안내("서비스 안정성을 높였어요")를 쓰고, 공지를 생략해도 된다고 함께 말한다.
- 릴리즈 노트의 "블로그 공지 문구"에 넣고, 채팅에도 그대로 붙여 넣을 수 있게 보여 준다.

## 5. 마무리 보고 (짧게)

- 배포된 버전과 태그, `/api/health`에서 `"version":"<버전>"`으로 확인하는 법
- 문서 저장소 Release 링크
- 공지 제목과 본문 (관리자 화면 → 공지 작성에 붙여 넣기)
