# One Blog Constitution

## Core Principles

### I. 요구사항 문서가 기준

- 무엇을 만들지는 `docs/requirements/`의 요구사항 분석서가 정한다. 스펙(`/speckit-specify`)은
  해당 요구사항 ID(USR-01, BLG-09 등)를 반드시 인용한다.
- 문서끼리 내용이 다르면 `08-decision-log.md`의 최신 결정이 우선한다.
- 구현 중에 요구사항을 바꾸거나 새로 정하면, 코드와 함께 해당 장과 8장 결정 기록을 같은
  커밋(또는 같은 PR)에서 고친다. 문서와 코드가 어긋난 채로 두지 않는다.
- 6장에서 상태가 **보류**인 항목은 팀이 확정하기 전까지 구현하지 않는다.

이유: 요구사항이 이미 97개의 결정으로 정리되어 있어, 에이전트와 팀원이 같은 기준을 봐야 한다.

### II. 핵심 기능 먼저, 점진적으로 세부화

- 기능은 끝까지 동작하는 작은 단위(화면 → API → DB)로 하나씩 완성한다. 여러 기능을 반쯤
  만들어 두지 않는다.
- 1단계 순서: 회원가입·로그인(USR-01~04) → 블로그 생성·목록·참여(BLG-01~06) →
  게시판 글·댓글(BRD-01~02, BRD-06). 소셜·알림·관리자·통계는 그 뒤에 붙인다.
- 각 기능의 첫 버전은 요구사항의 핵심 흐름만 구현하고, 세부 정책(6장 숫자, 예외 흐름,
  부가 기능)은 이후 반복에서 스펙을 갱신하며 추가한다. 미룬 항목은 스펙의 "후속 작업"에
  남겨 잊히지 않게 한다.

이유: 팀이 중요 기능부터 구현하고 정책·보안 세부를 차근차근 채우기로 했다.

### III. 처음부터 지키는 보안 기준선 (NON-NEGOTIABLE)

세부 보안 정책은 나중에 채워도 되지만, 아래 항목은 첫 코드부터 지킨다. 나중에 붙이면
이미 쌓인 코드와 데이터를 전부 고쳐야 하기 때문이다.

- 비밀번호는 bcrypt 해시로만 저장한다 (SEC-01).
- 블로그별 역할(블로그장·부블로그장·멤버)은 모든 요청에서 서버가 DB로 확인한다.
  화면이나 토큰 내용만 믿지 않는다 (SEC-07, SEC-11).
- SQL은 파라미터 바인딩(JPA/PreparedStatement)으로만 만든다. 문자열 이어 붙이기 금지.
- 사용자 입력은 화면에 `textContent`로 넣는다. `innerHTML`은 서버가 jsoup으로 거른 글 본문에만
  쓴다 (SEC-06).
- 이메일·전화번호 가리기는 서버가 응답을 만들 때 한다 (4.4).
- 비밀키·DB 비밀번호·SMTP 비밀번호는 저장소에 올리지 않는다. 환경변수나 git에서 제외된
  로컬 설정 파일로만 넣는다.

로그인 잠금, CAPTCHA, IP 요청 제한, 보안 헤더 세부 값 등은 세부화 단계에서 추가한다.

### IV. 나중에 바꾸기 비싼 구조는 처음부터

- DB 변경은 Flyway 마이그레이션 파일로만 한다. `ddl-auto=update`는 로컬에서도 쓰지 않는다.
- 핵심 테이블(회원·블로그·글·댓글 등)은 처음부터 `created_at`, `updated_at`, 그리고 30일 보관
  규칙(4.5)을 위한 `deleted_at`(소프트 삭제)을 둔다.
- 문자셋은 `utf8mb4`로 통일한다.
- 회원 ↔ 블로그는 블로그 멤버십(역할 포함) 테이블로 잇는다. 역할은 계정이 아니라 블로그별
  속성이다 (2장).
- 서버 메모리에 상태를 두지 않는다 (SCL-01). 파일 저장은 `FileStorage` 인터페이스 뒤에 둔다
  (SCL-02). `@Scheduled`에는 ShedLock을 걸고 `zone = "Asia/Seoul"`을 지정한다 (SCL-03).
- 새 기능에 필요한 테이블은 그 기능을 만들 때 마이그레이션으로 추가한다. 쓰지 않을 테이블을
  미리 만들지 않는다.

### V. 단순함 우선

- 1차는 서버 1대로 운영한다. Redis, S3, 로드밸런서는 이중화할 때 붙인다 (4.3).
- 요구사항에 없는 기능이나 추상화를 미리 만들지 않는다. 복잡한 선택을 할 때는 plan에 이유를
  적는다.

## 기술 스택과 제약

7장(구현 방식)에서 확정된 내용을 따른다.

- 백엔드: Spring Boot, Spring Security, Spring Data JPA, Flyway
- DB: MySQL 8 (검색은 FULLTEXT + ngram)
- 화면: 정적 HTML + JS(API 호출). 글 상세만 서버가 og 태그를 채움. 에디터는 Toast UI Editor
- 로그인: JWT(Access + Refresh) + HttpOnly·Secure 쿠키, Refresh Token은 DB 저장, CSRF 토큰 사용
- 메일: Gmail SMTP / 사람 확인: Cloudflare Turnstile
- 성능 목표: 메인·목록·검색 1~2초 안에 응답 (4.2)

## 개발 흐름

- 기능마다 `/speckit-specify` → `/speckit-plan` → `/speckit-tasks` → `/speckit-implement` 순서로
  진행한다. 모호한 부분이 있으면 plan 전에 `/speckit-clarify`를 쓴다.
- 권한이 걸린 기능은 "권한 없는 사용자가 요청하면 거부되는지"를 확인하는 테스트를 함께 만든다.
- 변경은 `main`에 바로 올린다. 커밋 메시지에 관련 요구사항 ID를 적는다.

## Governance

- 이 헌법은 다른 개발 관행보다 우선한다. 모든 plan은 "Constitution Check"에서 위 원칙을
  확인한다.
- 원칙을 바꾸려면 커밋 메시지에 변경 이유를 남기고 팀이 합의한다. 요구사항 결정이 바뀌어 원칙이
  바뀌는 경우 8장에도 기록한다.
- 버전 규칙: 원칙 삭제·재정의는 MAJOR, 원칙·섹션 추가는 MINOR, 문구 수정은 PATCH.
